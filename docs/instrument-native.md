# 参考现有熊猫固件实现自研仪表端

目标是适配原车仪表的自研服务与可验证更新包。参考材料为用户提供的宋版1.0.0与唐版1.0.3-1017；仅将静态样本用于确定互操作格式和平台契约，不发布其中的程序、资源或反编译代码。自研服务不设置登录、VIP或商业许可证，更新包继续校验签名、摘要、车型和硬件。

## 沿用的技术路径

`车机编码H.264 → USB NCM → BVL1握手/LHF2帧 → 原生接收服务 → mm-renderer/mdevpush → Screen窗口`

| 部分 | 参考固件观察 | 自研实现状态 |
| --- | --- | --- |
| 开机启动 | 可选扩展启动后继续OEM SLM；扩展模块各自带锁和校验 | 启动适配未实现；必须保留原车启动与故障退出路径 |
| USB | 原生角色后端、NCM驱动、切换及回读，不只是设置一个IP | 需对应仪表硬件实测；host接收器不改变USB角色 |
| 视频传输 | BVL1、LHF2、IEEE CRC32、Annex B H.264 | 自研C99校验核心与有界回环TCP会话已实现 |
| 解码 | ARM32 QNX程序连接mm-renderer，通过mdevpush送流 | 尚未实现QNX后端；不能用host文件写入冒充解码提交 |
| 显示 | Screen父/视频子窗口、窗口组、几何和可见性回读、post事件 | 尚未实现QNX窗口适配；不复制厂商HMI钩子 |
| 更新 | app.sv扩展服务；新版另有FUP2组件与整包更新路径 | 自签名FUP2与实验安装已实现，生产安装/恢复后端未实现 |

原生代码与复现实验见[`instrument/native/`](../instrument/native/README.md)。当前真实测试覆盖电脑上的编码、TCP收帧、文件还原与FFmpeg解码；没有运行目标QNX服务，没有完成实车显示或刷写。

## QNX后端需要满足的契约

静态样本调用`/base/usr/lib/libmmrndclient.so.1`中的mmr连接、context、input/output attach、参数和play接口。输出使用Screen窗口组；输入为`mdevpush:/dev/name/local/<会话名>`及H264尺寸、帧率参数。通道首次格式消息是八个本机小端u32：`0, 0x48323634, width, height, 24, fps, 0, 0`。这个本地消息格式与大端LHF2 TCP帧头不同。

正式实现需要目标兼容的QNX SDK/sysroot、解码插件及IPC契约，正确管理参数字典、连接、窗口和异常释放。仅有原始固件里的运行库不能证明可以替代SDK完成正确链接，也不能根据现有二进制的函数名猜测结构体或错误语义。

参考样本选中物理1920×720、display ID=2；这些是该样本的配置，不能写成宋、唐所有硬件的共同事实。编码尺寸与仪表物理尺寸分别配置。停止、拔线、解码失败时要释放所属视频窗口并恢复原车显示。

各状态必须分别记录：协议ready、负载接收、解码提交、Screen首个post、窗口属性回读、实际目视出画。ready、ACK或`playing`字段不能单独作为出画验收。

## 如何形成固件交付

宋、唐两份参考包的OS/MCU摘要相同，但app.sv中的HMI钩子、KZB资源和扩展服务有差异。以各自匹配的原车基础为边界，独立实现投屏服务并验证启动和窗口协作；不将唐的整套HMI/资源复制到宋，也不复制厂商鉴权程序再修改校验分支。

可刷包仍缺目标硬件身份、QNX原生编译/运行、生产安装目的地及重启契约、独立恢复入口和分别实车验证。当前不改写这些参考原包，也不发布占位刷机镜像。完成这些条件后再按车型/硬件/版本在GitHub Releases分发；实验程序与实验FUP2包不能刷入现成仪表。
